# 4.4.7 - Contrato de Telemetria

Este documento define o formato das mensagens trocadas entre o micromouse (ESP32) e o servidor (backend FastAPI): os campos de cada pacote, o cálculo do *checksum*, os eventos especiais e as regras de validação. O firmware, o backend e o frontend devem seguir este contrato; qualquer mudança nele exige alterar o campo de versão (`v`).

**Requisitos atendidos:** RF05-S (Transmissão de Telemetria), RF24-S (Validação de Pacotes de Telemetria) e RNF06-S (Latência de Telemetria). Também dá suporte a RF19-S, RF20-S, RF25-S, RNF07-S e RNF12-S.

---

## 1. Visão Geral

| Item | Definição |
| :--- | :--- |
| **Transporte** | WebSocket sobre Wi-Fi, do ESP32 (cliente) para o backend FastAPI (servidor), conforme a [Arquitetura da Solução](./4.4.3%20-%20Arquitetura%20da%20Solucao.md) |
| **Formato** | Uma mensagem por *frame* de texto do WebSocket, codificada em UTF-8 |
| **Conteúdo** | Objeto JSON (gerado no firmware com *ArduinoJson*) seguido de `\|` e do *checksum* em 4 dígitos hexadecimais |
| **Frequência** | Pacote de telemetria a cada **200 ms (5 Hz)**; eventos são enviados no instante em que ocorrem |
| **Versão** | `v = 1` |

Tipos de mensagem:

| `t` | Sentido | Uso |
| :--- | :--- | :--- |
| `tel` | Robô → Servidor | Leitura periódica de telemetria (vira uma linha de `leitura_telemetria`) |
| `evt` | Robô → Servidor | Evento especial: início e fim de corrida, bateria crítica, reconexão (vira uma linha de `log_evento`) |
| `ack` | Servidor → Robô | Confirmação de recebimento, usada para liberar o armazenamento local (RF25-S) |

---

## 2. Estrutura da Mensagem (*frame*)

```
<JSON>|<CRC>
```

* `<JSON>`: objeto JSON em uma única linha, sem espaços extras.
* `|`: separador. O backend procura a **última** ocorrência de `|` na mensagem.
* `<CRC>`: CRC-16 dos bytes de `<JSON>`, em 4 dígitos hexadecimais maiúsculos (ex.: `8653`).

O CRC é calculado sobre os **bytes exatos** do JSON enviado, e não sobre os valores já interpretados. Assim, o backend não precisa reconstruir o JSON nem se preocupar com a forma como o firmware formata números decimais: basta separar a mensagem no `|` e recalcular o CRC do trecho anterior.

---

## 3. Campos

### 3.1. Cabeçalho (comum a `tel` e `evt`)

| Campo | Tipo | Faixa válida | Descrição |
| :--- | :--- | :--- | :--- |
| `v` | inteiro | `1` | Versão do contrato |
| `t` | texto | `tel` ou `evt` | Tipo da mensagem |
| `corrida` | inteiro | ≥ 1 | Número da corrida no robô (contador gravado na memória não volátil do ESP32, incrementado a cada largada). Ver seção 7.1 |
| `seq` | inteiro | ≥ 0 | Número de sequência da mensagem dentro da corrida. Começa em 0 no evento `inicio` e aumenta de 1 em 1 em toda mensagem enviada (`tel` ou `evt`), sem lacunas |
| `tempo_ms` | inteiro | ≥ 0 | Horário da captura do dado, em milissegundos desde a largada (o ESP32 não tem relógio de data e hora). Corresponde à coluna `tempo_ms` |

### 3.2. Pacote de telemetria (`t = "tel"`)

Além do cabeçalho:

| Campo | Tipo | Faixa válida | Unidade | Coluna no banco | Descrição |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `pos_x` | inteiro | 0 até `largura_celula - 1` | célula | `pos_x` | Coluna da célula atual |
| `pos_y` | inteiro | 0 até `altura_celula - 1` | célula | `pos_y` | Linha da célula atual |
| `orientacao` | texto | `N`, `S`, `L`, `O` | - | `orientacao` | Direção para onde o robô está virado |
| `paredes` | inteiro | 0 a 15 | máscara de bits | - | Paredes da célula atual (ver 3.3) |
| `velocidade` | decimal | 0 a 5,000 | m/s | `velocidade` | Velocidade linear instantânea calculada pelos encoders, com 3 casas decimais |
| `tensao_bateria` | decimal | 0 a 9,00 | V | `tensao_bateria` | Tensão da bateria lida pelo INA226, com 2 casas decimais |
| `flood` | inteiro ou `null` | ≥ 0 | - | `valor_flood` | Valor de *flood* da célula atual; `null` se ainda não calculado |
| `estado` | texto | ver abaixo | - | - | Estado da navegação, exibido em "Status da Execução" |

Valores de `estado`: `explorando` (mapeando o labirinto), `retornando` (voltando à largada), `rapido` (percurso otimizado, RF13-S) e `parado`.

Todos os campos são obrigatórios; apenas `flood` aceita `null`. Campos desconhecidos são ignorados pelo backend, o que permite acrescentar campos novos sem quebrar versões antigas.

### 3.3. Codificação das paredes

As paredes usam as direções **absolutas** do labirinto (as mesmas de `orientacao`), e não a frente do robô. Cada bit indica uma parede presente:

| Bit | Valor | Parede |
| :--- | :--- | :--- |
| 0 | 1 | Norte (`N`) |
| 1 | 2 | Leste (`L`) |
| 2 | 4 | Sul (`S`) |
| 3 | 8 | Oeste (`O`) |

Exemplo: `paredes = 9` (1 + 8) significa paredes ao Norte e a Oeste. A conversão das leituras dos sensores (frente, esquerda, direita) para direções absolutas é feita no firmware, que já conhece a orientação (RF02-S). A parede traseira vem do giro de 180° ou da inferência descrita no RF01-S.

## 4. Eventos Especiais (`t = "evt"`)

Todo evento tem o cabeçalho da seção 3.1 e o campo `evento`. O backend grava cada evento em `log_evento` com `origem = 'firmware'`.

| `evento` | Quando é enviado | Campos adicionais | Efeito no backend | Tipo no log |
| :--- | :--- | :--- | :--- | :--- |
| `inicio` | Na largada, antes de qualquer `tel`. Sempre tem `seq = 0` e `tempo_ms = 0` | `tensao_bateria` | Associa a corrida do robô à corrida `em_andamento` do sistema web (seção 7.1) | `info` |
| `fim` | Ao chegar ao objetivo (RF04-S) ou ao abandonar a corrida | `resultado` (`concluida` ou `abandonada`); `tempo_conc_s` (obrigatório se `concluida`); `consumo_medio_ma`; `motivo` (obrigatório se `abandonada`) | Atualiza `status`, `tempo_conc_s` e `consumo_medio_ma` da corrida em uma única transação (RF07-S) | `info` se concluída, `aviso` se abandonada |
| `bateria_critica` | Quando a tensão fica abaixo de **7,0 V** (3,5 V por célula) por pelo menos 1 s. Só volta a ser enviado depois que a tensão passar de 7,2 V, para não repetir o alerta a cada oscilação | `tensao_bateria` | Registra o alerta; o frontend mostra o aviso (RF19-S) | `aviso` |
| `reconexao` | Logo após a conexão com o servidor ser restabelecida, antes do reenvio dos pacotes guardados | `offline_ms` (tempo sem conexão); `pendentes` (quantidade de mensagens guardadas que serão reenviadas) | Registra a queda e o retorno da conexão | `aviso` |

Valores de `motivo` em uma corrida abandonada: `bateria_critica`, `colisao`, `tempo_esgotado` e `manual` (botão de parada). O status `abandonada` cobre as corridas que o RF07-S chama de abortadas ou interrompidas.

## 5. Cálculo do *Checksum*

Algoritmo: **CRC-16/CCITT-FALSE**.

| Parâmetro | Valor |
| :--- | :--- |
| Polinômio | `0x1021` |
| Valor inicial | `0xFFFF` |
| Reflexão de entrada/saída | Não |
| XOR final | `0x0000` |
| Valor de verificação | CRC de `123456789` (ASCII) = `29B1` |

**Por que CRC e não uma soma simples:** a soma dos bytes não percebe bytes trocados de lugar nem vários erros que se compensam. O CRC-16 detecta qualquer erro em sequência de até 16 bits e custa poucas operações por byte no ESP32. O TCP já tem a sua própria verificação, mas ela não cobre erros gerados antes do envio, como um pacote montado com dados errados ou corrompido no armazenamento local (RF25-S). O CRC do contrato protege a mensagem desde a sua montagem até a validação no servidor (RNF07-S).

**Firmware (C++):**

```cpp
uint16_t crc16_ccitt(const uint8_t* dados, size_t n) {
  uint16_t crc = 0xFFFF;
  for (size_t i = 0; i < n; i++) {
    crc ^= (uint16_t)dados[i] << 8;
    for (int b = 0; b < 8; b++)
      crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : crc << 1;
  }
  return crc;
}
// Envio: snprintf(frame, tam, "%s|%04X", json, crc16_ccitt((uint8_t*)json, strlen(json)));
```

**Backend (Python):** a biblioteca padrão já implementa este CRC.

```python
import binascii

def crc16(dados: bytes) -> int:
    return binascii.crc_hqx(dados, 0xFFFF)

assert crc16(b"123456789") == 0x29B1
```

## 6. Validação no Backend (RF24-S)

Cada mensagem recebida passa pelas etapas abaixo, nesta ordem. A primeira falha encerra a validação: o pacote é descartado, **não** é gravado em `leitura_telemetria` nem exibido no dashboard, e o descarte é registrado em `log_evento` com `tipo = 'erro'`, `origem = 'backend'` e o motivo na `mensagem`. O servidor continua aceitando as mensagens seguintes.

| # | Verificação | Motivo registrado em caso de falha |
| :--- | :--- | :--- |
| 1 | A mensagem tem `\|` seguido de exatamente 4 dígitos hexadecimais | `formato invalido` |
| 2 | O CRC recalculado sobre o JSON é igual ao CRC recebido | `checksum invalido (recebido XXXX, calculado YYYY)` |
| 3 | O trecho antes do `\|` é um JSON válido | `json invalido` |
| 4 | `v` é uma versão suportada | `versao nao suportada` |
| 5 | Todos os campos obrigatórios estão presentes e com o tipo correto | `campo ausente: <nome>` ou `tipo invalido: <nome>` |
| 6 | Os valores estão dentro das faixas da seção 3 (incluindo `pos_x` e `pos_y` dentro das dimensões do labirinto da corrida) | `fora do intervalo: <nome>=<valor>` |

O motivo é o que aparece no campo "Motivo" da tela **Logs e Eventos** (CT-S03).

Mensagens com `seq` já recebido (reenvio após queda de conexão) são **válidas**: o backend as confirma com `ack` e não grava de novo. A restrição `UNIQUE (id_corrida, tempo_ms)` com `ON CONFLICT DO NOTHING` garante isso no banco ([Persistência de Dados](./4.4.4%20-%20Persistencia%20de%20Dados.md)). Mensagens fora de ordem também são válidas, já que a ordem real é dada por `tempo_ms` e `seq`.

## 7. Regras de Comunicação

### 7.1. Identificação da corrida
O robô pode largar sem conexão (CT-SE17), então não depende do servidor para numerar a corrida: o campo `corrida` é um contador local do ESP32. Ao receber o evento `inicio`, o backend associa esse número ao registro de `corrida` com status `em_andamento` criado pelo sistema web e passa a usar o `id` desse registro para gravar as leituras e os eventos.

### 7.2. Confirmação (`ack`) e reenvio
O servidor responde no mesmo formato de *frame*:

```
{"t":"ack","corrida":7,"seq":42}|7278
```

Cada mensagem válida recebe o seu próprio `ack`, com o mesmo `corrida` e `seq` dela. Pacotes descartados na validação não são confirmados. *(Uma confirmação cumulativa, do tipo "recebi tudo até o `seq` N", foi descartada porque um único pacote descartado travaria a confirmação de todos os seguintes).*

* O robô guarda cada mensagem enviada até receber a confirmação (RF25-S).
* Mensagens sem confirmação depois de 2 s são reenviadas, em ordem de `seq`.
* Depois de 3 reenvios sem confirmação, a mensagem é descartada pelo robô e registrada no log serial; a lacuna fica visível na numeração.

**Armazenamento local:** o firmware guarda cada leitura como uma estrutura binária (cerca de 20 bytes) e só monta o JSON na hora de enviar. Uma corrida de 10 minutos a 5 Hz gera 3.000 leituras, cerca de 60 KB, o que cabe na RAM do ESP32 dentro do limite do RNF03-S.

### 7.3. Perda de conexão
* **Servidor:** sem nenhuma mensagem por 3 s, marca o robô como *Offline* (CT-S06). Volta a *Online* na próxima mensagem válida.
* **Robô:** ao perder a conexão, continua navegando normalmente (RNF15-S), guarda as mensagens e tenta reconectar. Ao reconectar, envia o evento `reconexao` e depois as mensagens pendentes (RNF12-S).

### 7.4. Latência (RNF06-S)
A latência é medida pela diferença entre o instante de captura no robô e o instante de exibição no dashboard. Como `tempo_ms` é relativo à largada, o backend estima o instante absoluto da largada como o **menor valor de `recebido_em - tempo_ms`** entre as mensagens recebidas ao vivo na corrida. Usar o menor valor evita que pacotes reenviados após uma queda distorçam a referência.

```
latencia = instante_de_exibicao - (largada_estimada + tempo_ms)
```

A estimativa subestima a latência real apenas pelo menor atraso de rede observado, que em rede local é de poucos milissegundos. Para que a medição seja possível, o backend repassa `tempo_ms` sem alteração ao frontend.

Orçamento de tempo para cumprir o limite de 500 ms:

| Etapa | Tempo máximo |
| :--- | :--- |
| Captura até a fila de envio no ESP32 (*Core 1* → *Core 0*) | 50 ms |
| Transmissão Wi-Fi até o servidor | 150 ms |
| Validação, gravação e repasse no backend | 100 ms |
| Recebimento e renderização no frontend | 100 ms |
| **Total (folga de 100 ms)** | **400 ms** |

## 8. Exemplos

### 8.1. Pacote de telemetria válido

```
{"v":1,"t":"tel","corrida":7,"seq":42,"tempo_ms":8400,"pos_x":2,"pos_y":1,"orientacao":"L","paredes":9,"velocidade":0.312,"tensao_bateria":7.86,"flood":3,"estado":"explorando"}|8653
```

Leitura: 42ª mensagem da corrida 7, capturada 8,4 s após a largada. O robô está na célula (2, 1), virado para Leste, com paredes ao Norte e a Oeste, a 0,312 m/s, com bateria em 7,86 V, explorando o labirinto, em uma célula com valor de *flood* 3. O CRC recalculado é `8653`, igual ao recebido: o pacote é aceito.

### 8.2. Pacote corrompido

```
{"v":1,"t":"tel","corrida":7,"seq":42,"tempo_ms":8400,"pos_x":3,"pos_y":1,"orientacao":"L","paredes":9,"velocidade":0.312,"tensao_bateria":7.86,"flood":3,"estado":"explorando"}|8653
```

É o mesmo pacote do exemplo 8.1 com um único caractere alterado (`pos_x` de 2 para 3). O CRC recalculado sobre o JSON recebido é `B9F4`, diferente do `8653` informado. O pacote falha na etapa 2 da validação, é descartado e gera em `log_evento`:

| `tipo` | `origem` | `mensagem` |
| :--- | :--- | :--- |
| `erro` | `backend` | `checksum invalido (recebido 8653, calculado B9F4)` |

Note que o pacote corrompido é um JSON perfeitamente válido e com valores dentro das faixas: sem o *checksum*, a posição errada seria gravada sem que ninguém percebesse.

### 8.3. Eventos

```
{"v":1,"t":"evt","corrida":7,"seq":0,"tempo_ms":0,"evento":"inicio","tensao_bateria":8.21}|4886
{"v":1,"t":"evt","corrida":7,"seq":97,"tempo_ms":19350,"evento":"bateria_critica","tensao_bateria":6.98}|8E50
{"v":1,"t":"evt","corrida":7,"seq":160,"tempo_ms":32010,"evento":"reconexao","offline_ms":20150,"pendentes":101}|1D4F
{"v":1,"t":"evt","corrida":7,"seq":311,"tempo_ms":62240,"evento":"fim","resultado":"concluida","tempo_conc_s":62.24,"consumo_medio_ma":412.5}|E1BA
{"v":1,"t":"evt","corrida":8,"seq":55,"tempo_ms":11020,"evento":"fim","resultado":"abandonada","motivo":"bateria_critica","consumo_medio_ma":398.0}|0C0B
```

O tamanho máximo de uma mensagem é de cerca de 200 bytes. A 5 Hz, a telemetria ocupa por volta de 1 KB/s, muito abaixo da capacidade do Wi-Fi do ESP32.

## 9. Rastreabilidade

| Requisito | Onde é atendido neste contrato |
| :--- | :--- |
| **RF05-S** | Seções 1 a 4: transporte, formato, campos, frequência e eventos |
| **RF24-S** | Seções 5 e 6: CRC-16 e etapas de validação com registro do descarte |
| **RNF06-S** | Seções 3.1 (`tempo_ms`) e 7.4: medição da latência e orçamento de tempo |
| **RF19-S** | Evento `bateria_critica` e regra de *Offline* após 3 s |
| **RF20-S** | Gravação dos eventos e dos descartes em `log_evento` |
| **RF25-S / RNF12-S** | `seq`, `ack` por mensagem, reenvio e evento `reconexao` |
| **RNF07-S** | CRC na recepção e descarte de pacotes inválidos antes da gravação |
