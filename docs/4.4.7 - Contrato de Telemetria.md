# 4.4.7 - Contrato de Telemetria

Formato das mensagens entre o micromouse (ESP32) e o servidor (FastAPI). Firmware, backend e frontend seguem este contrato; qualquer mudança exige incrementar o campo `v`.

**Requisitos:** RF05-S, RF24-S e RNF06-S (apoia RF19-S, RF20-S, RF25-S, RNF07-S e RNF12-S).

---

## 1. Formato

* **Transporte:** WebSocket, um *frame* de texto por mensagem.
* **Frequência:** telemetria a cada **200 ms (5 Hz)**; eventos no instante em que ocorrem.
* **Mensagem:** JSON em uma linha + `|` + CRC-16 do JSON em 4 dígitos hexadecimais maiúsculos.

```
<JSON>|<CRC>
```

| `t` | Sentido | Uso |
| :--- | :--- | :--- |
| `tel` | Robô → Servidor | Telemetria periódica (grava em `leitura_telemetria`) |
| `evt` | Robô → Servidor | Evento especial (grava em `log_evento`) |
| `ack` | Servidor → Robô | Confirma o recebimento de uma mensagem |

---

## 2. Campos

### 2.1. Cabeçalho (`tel` e `evt`)

| Campo | Tipo | Descrição |
| :--- | :--- | :--- |
| `v` | inteiro | Versão do contrato (`1`) |
| `t` | texto | `tel` ou `evt` |
| `corrida` | inteiro ≥ 1 | Número da corrida no robô (contador salvo no ESP32). O backend associa ao registro `em_andamento` ao receber o evento `inicio` |
| `seq` | inteiro ≥ 0 | Sequência da mensagem na corrida: começa em 0 no `inicio` e sobe de 1 em 1, sem lacunas. Usado só no transporte (`ack` e reenvio); não é gravado no banco |
| `tempo_ms` | inteiro ≥ 0 | Milissegundos desde a largada no momento da captura |

### 2.2. Telemetria (`t = "tel"`)

| Campo | Tipo | Faixa | Unidade |
| :--- | :--- | :--- | :--- |
| `pos_x` | inteiro | 0 a `largura_celula - 1` | célula |
| `pos_y` | inteiro | 0 a `altura_celula - 1` | célula |
| `orientacao` | texto | `N`, `S`, `L`, `O` | - |
| `paredes` | inteiro | 0 a 15 | máscara de bits (abaixo) |
| `velocidade` | decimal (3 casas) | 0 a 5,000 | m/s |
| `tensao_bateria` | decimal (2 casas) | 0 a 9,00 | V |
| `valor_flood` | inteiro ou `null` | ≥ 0 | - |
| `estado` | texto | `explorando`, `retornando`, `rapido`, `parado` | - |

**Paredes** (direções absolutas do labirinto, somar os valores presentes):

| Norte | Leste | Sul | Oeste |
| :---: | :---: | :---: | :---: |
| 1 | 2 | 4 | 8 |

Exemplo: `9` = Norte + Oeste.

Todos os campos são obrigatórios (só `valor_flood` aceita `null`). Campos desconhecidos são ignorados.

**Persistência:** cada `tel` vira uma linha de `leitura_telemetria` (ver 4.4.4); os campos de mesmo nome vão direto para a coluna, e `corrida` é traduzido para `id_corrida` pelo backend. O `estado` não é gravado: só é repassado ao frontend para o "Status da Execução" em tempo real.

---

## 3. Eventos (`t = "evt"`)

Cabeçalho + campo `evento`:

| `evento` | Quando | Campos extras | Tipo no log |
| :--- | :--- | :--- | :--- |
| `inicio` | Na largada (`seq = 0`, `tempo_ms = 0`) | `tensao_bateria` | `info` |
| `fim` | Objetivo alcançado ou corrida abandonada | `resultado` (`concluida`/`abandonada`), `tempo_conc_s` (se concluída), `consumo_medio_ma`, `motivo` (se abandonada: `bateria_critica`, `colisao`, `tempo_esgotado`, `manual`) | `info` / `aviso` |
| `bateria_critica` | Tensão < 7,0 V por 1 s (só repete depois de voltar acima de 7,2 V) | `tensao_bateria` | `aviso` |
| `reconexao` | Logo após reconectar, antes de reenviar os pendentes | `offline_ms`, `pendentes` | `aviso` |

---

## 4. Checksum

**CRC-16/CCITT-FALSE** (polinômio `0x1021`, inicial `0xFFFF`, sem reflexão, XOR final `0`), calculado sobre os bytes exatos do JSON. Teste: CRC de `123456789` = `29B1`.

**Firmware (C++):**

```cpp
uint16_t crc16_ccitt(const uint8_t* dados, size_t n) {
  uint16_t crc = 0xFFFF;
  for (size_t i = 0; i < n; i++) {
    crc ^= (uint16_t)dados[i] << 8;
    for (int b = 0; b < 8; b++)
      crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : crc << 1;
  }
  return crc;
}
// snprintf(frame, tam, "%s|%04X", json, crc16_ccitt((uint8_t*)json, strlen(json)));
```

**Backend (Python):**

```python
import binascii
crc = binascii.crc_hqx(json_bytes, 0xFFFF)  # crc_hqx(b"123456789", 0xFFFF) == 0x29B1
```

## 5. Validação no backend (RF24-S)

Na primeira falha, o pacote é descartado (não grava, não exibe) e é registrado em `log_evento` com `tipo = 'erro'`, `origem = 'backend'` e o motivo:

| # | Verificação | Motivo no log |
| :--- | :--- | :--- |
| 1 | Termina em `\|` + 4 dígitos hexadecimais | `formato invalido` |
| 2 | CRC recalculado = CRC recebido | `checksum invalido (recebido XXXX, calculado YYYY)` |
| 3 | JSON válido | `json invalido` |
| 4 | `v` suportado | `versao nao suportada` |
| 5 | Campos obrigatórios presentes e com o tipo certo | `campo ausente: <nome>` / `tipo invalido: <nome>` |
| 6 | Valores dentro das faixas (posição dentro do labirinto) | `fora do intervalo: <nome>=<valor>` |

Mensagem repetida (reenvio) é válida: o servidor confirma com `ack` e não grava de novo.

* **`tel`:** a leitura com `tempo_ms` já gravado na corrida é ignorada pela restrição `UNIQUE (id_corrida, tempo_ms)` (`ON CONFLICT (id_corrida, tempo_ms) DO NOTHING`).
* **`evt`:** como `log_evento` não tem restrição de unicidade, o backend guarda os pares (`corrida`, `seq`) já recebidos na corrida em andamento e ignora o evento repetido.

---

## 6. Regras de comunicação

* **Ack:** o servidor responde a cada mensagem válida com `{"t":"ack","corrida":7,"seq":42}|7278`. Pacote descartado não recebe `ack`.
* **Reenvio (RF25-S):** o robô guarda cada mensagem até receber o `ack`. Se o `ack` não chegar em 2 s, reenvia; depois de 3 tentativas, descarta a mensagem.
* **Queda de conexão:** o servidor marca o robô como *Offline* depois de 3 s sem mensagens. O robô continua navegando (RNF15-S), guarda as mensagens e, ao reconectar, envia `reconexao` e depois os pendentes.
* **Latência (RNF06-S):** largada estimada = menor `recebido_em - tempo_ms` da corrida; latência = instante de exibição − (largada estimada + `tempo_ms`). O backend repassa `tempo_ms` ao frontend sem alterar. Limite: 500 ms.

---

## 7. Exemplos

**Válido:** corrida 7, célula (2, 1), virado para Leste, paredes Norte + Oeste.

```
{"v":1,"t":"tel","corrida":7,"seq":42,"tempo_ms":8400,"pos_x":2,"pos_y":1,"orientacao":"L","paredes":9,"velocidade":0.312,"tensao_bateria":7.86,"valor_flood":3,"estado":"explorando"}|2917
```

**Corrompido:** o mesmo pacote com `pos_x` alterado de 2 para 3. O CRC calculado é `8E28` ≠ `2917`, então o pacote é descartado com o motivo `checksum invalido (recebido 2917, calculado 8E28)`.

```
{"v":1,"t":"tel","corrida":7,"seq":42,"tempo_ms":8400,"pos_x":3,"pos_y":1,"orientacao":"L","paredes":9,"velocidade":0.312,"tensao_bateria":7.86,"valor_flood":3,"estado":"explorando"}|2917
```

**Eventos:**

```
{"v":1,"t":"evt","corrida":7,"seq":0,"tempo_ms":0,"evento":"inicio","tensao_bateria":8.21}|4886
{"v":1,"t":"evt","corrida":7,"seq":97,"tempo_ms":19350,"evento":"bateria_critica","tensao_bateria":6.98}|8E50
{"v":1,"t":"evt","corrida":7,"seq":160,"tempo_ms":32010,"evento":"reconexao","offline_ms":20150,"pendentes":101}|1D4F
{"v":1,"t":"evt","corrida":7,"seq":311,"tempo_ms":62240,"evento":"fim","resultado":"concluida","tempo_conc_s":62.24,"consumo_medio_ma":412.5}|E1BA
{"v":1,"t":"evt","corrida":8,"seq":55,"tempo_ms":11020,"evento":"fim","resultado":"abandonada","motivo":"bateria_critica","consumo_medio_ma":398.0}|0C0B
```
