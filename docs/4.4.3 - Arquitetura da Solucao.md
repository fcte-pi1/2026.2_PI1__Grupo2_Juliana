# 4.4.3 - Arquitetura da Solução de Software

Esta seção detalha o modelo arquitetural do software do Micromouse, as escolhas tecnológicas e a modelagem estruturada segundo as Visões 4+1 do Processo Unificado (UP).

### 1. Propósito do Software
O software do Micromouse atua como o núcleo de inteligência e monitoramento do sistema. Seu papel é duplo: no ambiente embarcado (robô), capta dados físicos (sensores e giroscópio), calcula a rota mais eficiente (algoritmo Flood Fill) e controla a atuação dos motores em tempo real. No ambiente externo, atua como uma plataforma de telemetria, processando e exibindo dados de desempenho, bateria, status e mapeamento do labirinto em uma interface web.

### 2. Padrões Adotados
O projeto adota o padrão **Cliente-Servidor Distribuído**. A justificativa deve-se à separação de responsabilidades: o robô (cliente IoT) não possui capacidade computacional para hospedar um site pesado, focando no controle de tempo real. Dentro do servidor Back-end, adota-se o padrão arquitetural **MVC (Model-View-Controller) / Arquitetura em Camadas (Layered)**. O framework gerencia rotas de comunicação (Controllers) e os esquemas de regras de negócio (Models), enquanto a camada de visualização (View) fica totalmente desacoplada e delegada ao Front-end.

### 3. Linguagens de Programação
*   **C++:** Utilizado exclusivamente no firmware do robô para garantir alto desempenho e gerenciamento explícito de memória.
*   **Python:** Utilizado no servidor Back-end pela agilidade de desenvolvimento e ecossistema robusto para conexões WebSocket.
*   **JavaScript / TypeScript:** Utilizado no Front-end como linguagem padrão para interações dinâmicas.

### 4. Frameworks e Bibliotecas
*   **Firmware:** Framework *Arduino-ESP32* no ambiente *PlatformIO*. Utiliza *FreeRTOS* para concorrência de tarefas e *ArduinoJson* para formatação.
*   **Back-end:** *FastAPI* como framework principal para rotas e WebSocket. O ORM do banco utiliza *SQLAlchemy 2* e *Alembic* para migrações.
*   **Front-end:** *React* para a SPA (Single Page Application). API nativa *Canvas 2D* para a renderização da malha do labirinto.

### 5. Modelagem Arquitetural (Visões 4+1)
Substituindo a visão de Casos de Uso pela Visão de Dados, conforme diretriz do projeto:

*   **I. Visão Lógica:** Dividida em Lógica Embarcada (Flood Fill em C++), Controle Físico (drivers) e Módulo Web (API REST/WebSocket).
*   **II. Visão de Processos:** O **FreeRTOS** garante a resposta crítica de 50 ms. O *Core 0* opera a rede Wi-Fi; o *Core 1* opera a navegação física. Dados trafegam via filas em RAM (`xQueue`).
*   **III. Visão de Implementação:** O repositório modulariza os pacotes estruturais em `src/firmware`, `src/backend` e `src/frontend`. 
*   **IV. Visão de Implantação (Física):** Nó Embarcado (microcontrolador ESP32) com suporte a OTA. Nó do Servidor (API Python, DB PostgreSQL) executado localmente.
